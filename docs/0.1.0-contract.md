# STAK 0.1.0 — Signed-in Product Contract (P0)

Status: **P0 — contract & model closure** (docs/spec only; no schema, no CLI, no UI).
This is the engineering contract that every later phase (P1–P10) builds against. Where
the design and this contract disagree, **this contract wins on data/architecture; the
design wins on UI, copy and hierarchy** (per the implementation brief). It contains no
per-project Memory mode, no unresolved VERIFY item, and none of the removed commands.

Sources reconciled: the final design contract (`STAK Final Contract.dc.html`, imported via
the design MCP — requires `/design-login`; read before P4) and the **STAK 0.1.0 Product
Contract Audit**. Everything below is already true in code unless marked **NEW**.

---

## 0. Non-negotiable invariants (hold in every phase)

- Preserve the frozen Memory crypto/format constants (`stack-project-compat-v1`,
  `stack-mem-remote-v1`, `stack-mem-bundle-v1`, `stack-mem-cipher-v1`,
  `stack-mem-bridge-v1`, `stack-memory-recovery-v1`, `stack-memory-passkey-v1`,
  `stack-memory-bridge-v1`, `stack-mem-device-mmk-v1`, `stack-memory-recovery-file-v1`),
  `.stackkey`, Project IDs, legacy `~/.stack` adoption, `STAK_*`/`STACK_*` env
  compatibility, every existing backup, local-only project bindings, and Standard/Protected
  semantics.
- Memory privacy mode is **account-wide**. Never model, store, or display a per-project mode.
- Check-in **never** uploads absolute local paths, **never** a home-relative locator (see
  §3 ENG DECISION), and **never** raw Memory content. Protected Memory stays ciphertext
  server-side and is never readable by Cloud.
- **No daemon, no background sync.** State changes only during CLI operations the user runs.
- **Never mutate a remote machine.** Web actions write account-side _desired_ state only;
  machines realise it on their next CLI run.
- Capabilities come from **declared metadata only**; when absent, show "Capabilities not
  declared". Never infer permissions from prose or skill bodies.
- Updates **fail closed**: Local/dirty/ambiguous/pinned sources show "Can't check for updates
  from this source"; an unreachable network operation shows "Check failed" instead (§5a);
  neither ever claims a false "Update available".

### Commands

Use existing commands exactly where they exist. **Build only** these new commands:
`stak skill update [<skill>]`, `stak skill pause <skill>`, `stak skill resume <skill>`,
`stak open`. **Extend** `stak status` to also perform the explicit check-in without
breaking its current local-readiness output.

These must **never appear anywhere**: `stak restore`, `stak stack apply`,
`stak project locate`.

**FUTURE (do not build in 0.1.0):** "Turn into a Skill", per-project stack apply, remote
machine actions, static analysis of skill bodies, public-stack usage counts, a general
activity/events table.

## 1. Memory model (account-wide)

- Privacy mode lives on `MemoryProfile.privacyMode` ∈ {`standard`, `protected`} — **one per
  account**. A backup is wholly Standard or Protected; `stak memory protect` migrates all
  existing generations. Manifest items have no mode.
- **Standard** — "Backed up": `mode = standard AND last_backup exists`. Private to your
  account; STAK's service can read it to deliver it. Don't say "encrypted"/"only you".
- **Protected** — "Protected": `mode = protected AND last_backup exists`. Encrypted on your
  machine before upload; Cloud stores only ciphertext and can't read it. Don't say "safe
  (alone)"/"synced".
- **Not backed up yet**: `last_backup is null`.
- UI: a single account-wide mode banner. A per-project **table is allowed** (files, last
  backup, last change) but **must not** carry a mode/"KEPT AS" column, and Settings must not
  offer a per-project mode. "New projects keep Memory as…" / "change per project" copy is
  removed.

### Memory read-model data availability (P3 — **frozen**)

The Cloud read model (`GET /memory/view`) exposes different fields by mode, because Protected
payloads are ciphertext the Cloud **cannot and must not** decrypt:

| Field                                                   | Standard                                                                                                                | Protected                                |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| privacy mode                                            | ✅                                                                                                                      | ✅                                       |
| latest backup time / backup history (generation + time) | ✅                                                                                                                      | ✅ (account metadata outside ciphertext) |
| recovery-method state (passkey / recovery file)         | ✅                                                                                                                      | ✅                                       |
| **per-project file/item counts** (`perProject`)         | ✅ **where derivable** — from the server-readable Standard bundle manifest, via an **authenticated, bounded** read path | **❌ `null` (unavailable)**              |

- For **Protected**, `perProject` is **always `null`**. The Cloud never decrypts the bundle to
  obtain per-project counts. The final design illustrates Protected with per-project file
  counts; **engineering truth wins** — P4/P6 must render Protected honestly and must **not**
  reconstruct or fake those values, e.g. "Protected · Backed up \<time\> · N projects known to
  STAK" (project count comes from the account-side `cloud_projects` registry, not the
  ciphertext). The per-project table above is therefore **Standard-only**.
- This availability contract may change only via a future **privacy-reviewed** design that
  introduces safe metadata persisted **outside** the ciphertext. Until then it is frozen.

## 2. Recover → Restore → Map (the new-machine sequence)

Two distinct real commands; **never** a root `stak restore`:

- `stak memory recover` — Cloud → this machine's **private STAK store** (`~/.stak/memory/`).
  Protected requires a passkey (browser) or recovery file. Does not touch agent files.
- `stak memory restore` — private store → **native agent Memory files**; writes only absent
  targets (never overwrites), gated by project availability/mapping.

A brand-new machine: `install CLI → stak login (approve) → stak memory recover
(+ passkey/recovery file if Protected) → stak memory restore → stak project map <unavailable
projects>`. The web presents **one guided "Bring your STAK here" outcome** that sequences and
_shows_ these real commands (web cannot run them); both terms stay visible because they mean
different things.

## 3. Machine check-in model (**NEW**)

No daemon. The CLI reports machine state **best-effort** during user-run operations.

**Payload (V0):** `machine_id`, friendly `name`, `platform`, `arch`, `agents_detected[]`,
`last_checkin`, `skills: [{ skillId, installed_version }]`, `projects: [{ projectId,
present: boolean }]`.

**Privacy rules (hard):**

- **No absolute paths. No home-relative path either.** Project state is **presence only**.
- No raw Memory content. Protected payloads never decrypted server-side.
- No credentials in errors.

**ENG DECISION — home-relative project locator: RESOLVED = do not ship.** STAK 0.1.0 Cloud
does **not** persist any project path/locator (absolute or home-relative). Check-in reports
presence only. The viewing machine may read its own local path locally where needed, but
Cloud never stores or returns it. (Addendum §5.)

### Project registry & lifecycle authority (P3 — **frozen**)

Lifecycle is **one logical account-level state**. The account-side `cloud_projects` registry
(stable Project ID, lifecycle, safe display name) accepts two STRICTLY separated inputs:

- **Discovery sync** (`POST /projects/sync`, from the CLI) says only _"this stable Project
  exists, with this safe display name"_. It carries **no lifecycle**: it creates a missing row
  (defaulting `active`) and refreshes the safe name, but **never** changes an existing row's
  lifecycle. So a machine with **stale local state can never silently un-archive** a Project the
  account archived (and vice-versa). Discovery must never masquerade as lifecycle intent.
- **Explicit lifecycle intent** (`POST /projects/:id/lifecycle`) is the **sole authority** for
  the Cloud lifecycle. Both the **web** action and the **CLI** `stak project archive/unarchive`
  (which, when authenticated and online, mirrors its local Phase-15 change to Cloud via this
  same endpoint) write it. **Last explicit write wins.**
- **Offline / Cloud-unreachable CLI:** the local Phase-15 lifecycle still changes (offline-capable),
  and the CLI prints a truthful warning that **Cloud was not updated** and to re-run the command
  when connected. Re-running the explicit command while connected — **even if the local state is
  already in that lifecycle** — re-attempts the Cloud write, so it reconciles. This is the V0
  reconciliation path: **no background daemon/outbox**, local and Cloud may differ transiently
  and that difference is always reported, never silently resolved by last-write-wins discovery.
- **Privacy:** the safe `name` is **account metadata**, derived only from a strong Git identity
  (`host/owner/repo`). A Local project's path-derived vendor key is **never** sent as a name; no
  path, Memory content, or Git credential is stored in `cloud_projects`. Lifecycle changes never
  affect presence, bindings, Memory, or local files. `stak project map` stays **local-only** —
  the web never maps a folder.

**Triggers** (emit after the operation succeeds, where machine state materially changes):
`login`, `status` (the explicit check-in), `memory backup`, `memory recover`,
`memory restore`, `use`, `run`, `scan`, `project map`, `skill update`, `skill pause`,
`skill resume`. Audit `push`/`pull`/`remove` and add check-in only where resulting machine
state materially changes.

**Failure semantics (Addendum §2):**

- Connectivity failure (network unreachable, timeout, temporary 5xx) → **non-fatal**; the
  parent local operation continues where safe; check-in is skipped silently.
- Explicit **401/403** → **not** treated as offline; surfaced distinctly. A revoked/invalid
  machine must never appear successfully checked in.

**Derived states (read model, not stored as truth):**

- _Up to date_ — at last check-in every Ready skill's installed version matched STAK's
  approved version AND Memory was backed up. Always shown with the check-in time.
- _Updates waiting_ — any approved skill version differs from the machine's installed
  version at last check-in.
- _Last seen \<time\>_ — `last_checkin`. Never "online/offline".

## 4. STAKs: `stak use <stak>` composes into `main`

`stak use <stak>` is "apply a STAK" and composes into the **`main` environment** (not a
per-project folder). Keep `stak.yaml`, `extends`, the resolver, conflict planning, and the
existing **dry-run preview** (`stak use <stak> --dry-run` prints the plan). Public STAKs
and inspect-before-use exist. The design's "apply to \<project\>" is reframed as composing
into `main`; per-project apply is **FUTURE**. `stak stack apply` must never appear.

## 5. Skill update model (source / desired / installed)

Three versions:

- **source** — the exact **immutable revision** the tracked Git ref (or public-stack/package
  version) currently resolves to.
- **desired (approved)** — the version approved in STAK; approving creates a **new imported
  version**, account-side only. Never touches a machine.
- **installed** — per-machine, reported at check-in.

Rules:

- _Update available_ (Git source) = tracked ref resolves to a **different exact revision**
  than the approved one. **Identity comparison** of resolved revisions — never lexical or
  numeric comparison of hashes (Addendum §4). Public-stack/package sources use that source's
  real version semantics.
- **Fail closed** for Local, dirty, ambiguous, or pinned sources: "Can't check for updates
  from this source"; an unreachable network operation is "Check failed", not cannot-check
  (§5a's precise boundary); neither ever claims a false "Update available".
- `stak skill update [<skill>]` installs approved versions **on this machine** and reports
  failures at check-in. Web approval only sets desired state; each machine installs on its
  next CLI run. "Update failed on \<machine\>" surfaces from that machine's next check-in.

## 5a. Skill review artifacts (**NEW**, P5a — local-CLI-plane source checking)

**Responsibility model (frozen):**

- **Local CLI** resolves Skill sources using the user's own local Git/network credentials,
  freezes the exact immutable candidate revision/version, materializes both the candidate
  subtree and the currently-approved subtree, computes the full STAK `candidateContentHash`,
  computes a deterministic diff, and uploads a bounded review artifact.
- **Cloud** never fetches arbitrary Git remotes and never possesses private Git credentials.
  It stores the latest source-check result and (when an update exists) one bounded review
  artifact per Skill, serves owner-scoped review data, and validates approval against the
  stored artifact and the Skill's current approved base.
- **Web** displays the latest CLI-reported source state and the exact stored artifact; it
  approves exactly that artifact and never resolves upstream itself.
- **Local apply** (`stak skill update <skill>`) re-materializes the approved immutable
  restoration reference and **must** verify the resulting content hashes to the approved
  `expectedContentHash` before changing any projected Skill file — failing closed, never
  projecting unverified content.

**Trust model for `candidateContentHash` (frozen):** a diff-only artifact does not contain
the complete candidate tree, so Cloud cannot and does not claim to independently recompute
the full tree hash. The authenticated CLI is the sole producer of `candidateRevision` +
`candidateContentHash`. Cloud validates schema, ownership, base identity, payload integrity
(via a separate `artifactPayloadHash`, §below) and bounds — never a fabricated "Cloud
re-verified the full tree" claim. The only point full-hash verification against the real tree
happens again is **local apply**, which re-materializes the content itself.

**Source-check has three data conditions (frozen; replaces the two-state assumption in §5
above for the checkable-source case):**

- **A. Checked — no update.** Latest CLI check found source identity == approved identity.
- **B. Checked — update available.** Latest CLI check found a real candidate. This SOURCE fact
  is independent of whether Cloud can show it: see "Oversized review" below.
- **C. Not checked / no current result.** The source may be checkable, but no valid
  CLI-reported check exists for the _current_ approved base. This is **not** "Can't check for
  updates from this source" — that phrase stays reserved for genuine structural inability
  (Local, dirty/ambiguous, exact-pinned/no-tracked-ref, resolution failure). Condition C uses
  descriptive text — **"Updates haven't been checked yet."** — with local guidance
  `stak skill check <skill>`. No new primary badge is introduced; the frozen vocabulary in
  §10 is unchanged (Ready · Update available · Paused · the cannot-check note); condition C is
  a plain secondary sentence, same pattern as the other non-badge neutral texts already
  established for unknown/unreconciled install state.

**Oversized review is a REVIEW CAPABILITY fact, never a check failure (frozen):** a candidate
that exceeds V0 review bounds (§16) is still reported as condition B —
`sourceCheckState: 'update-available'` — because the source resolution genuinely succeeded.
Cloud separately records `reviewUnavailableReason: 'exceeds-review-bounds'` (mutually
exclusive with holding a `reviewArtifactId` — a Skill has one or the other, never both). The
web still shows the primary badge **Update available**, never a 5th badge word, with a plain
secondary sentence — **"This update is too large to review in STAK Cloud."** — and no working
Approve action. This must never be represented as `check-failed`: the check did not fail, only
the review artifact could not be produced.

**Cannot-check vs. check-failed — the precise boundary (frozen):** `cannotCheckReason` is
reserved for exactly `{local, dirty, ambiguous, pinned}` — intrinsic facts about the Skill's
own restoration record, each computable with **zero network I/O**. Any outcome that required a
network operation which did not succeed — DNS failure, timeout, connection refused, a Git host
temporarily unavailable, authentication required or denied for a normally-checkable private
remote, a transient public-stack service failure — is **always** `check-failed`, **never**
`cannot-check`, regardless of how permanent it might turn out to be: the next check might
succeed. A transient failure preserves a safe `checkedAt` + a sanitized failure reason (never
raw Git stderr, which may contain credentials/URLs) and is reported as "Check failed" —
distinct from the permanent structural judgment "Can't check for updates from this source." A
temporary failure must never be converted into a permanent cannot-check capability claim, and
an intrinsic structural fact must never be reported as a retryable failure.

**Base-bound results (frozen):** every source-check result/review artifact records the
`approvedContentHash` it was computed against. A result is current only while
`artifact.approvedContentHash == Skill.approvedContentHash`. If approval changes, the old
result is no longer a valid current review and **may be deleted immediately in V0** — never
shown as a diff against the wrong approved base. Pause/resume alone does **not** invalidate a
review artifact, because it does not change approved content.

**Stale / superseded semantics (frozen — replaces the prior assumption that approval must
re-resolve the moving upstream ref at click time):**

- Artifact A created, upstream later moves to B, no newer `stak skill check` has run ⇒ **A
  remains approvable.** A is immutable and exactly what was reviewed; Cloud does not
  independently know or care that upstream moved. The next `stak skill check` will separately
  surface B as its own update-available fact.
- Artifact A exists, a later `stak skill check` uploads artifact B for the same Skill/base ⇒
  **B supersedes A; A is no longer approvable.** An old browser tab submitting A returns an
  explicit stale/superseded-review conflict.
- Artifact A exists, the Skill's approved content changes before A is approved ⇒ **A is stale
  because its approved base no longer matches; reject it.**

**Latest-only retention (frozen):** V0 keeps only the latest current source-check/review
artifact per Skill — no artifact history product. Replacement is safe: the new artifact's
metadata commits successfully _before_ the old blob is removed, so a failed/interrupted
upload never loses the previously-valid review. Retry is idempotent.

**Durable cleanup obligation (frozen, final micro-gate — replaces best-effort-only deletion):**
deleting a superseded or consumed artifact's blob payload is never a fire-and-forget
`catch(() => undefined)`. Every write that supersedes or consumes an artifact records that
artifact's id in the owning `(userId, skillId)` row's `pendingCleanupArtifactIds` list **in the
same commit** that performs the supersession/consumption — the obligation is durable the
instant the metadata switch lands, never an afterthought a failed delete can silently lose. The
service then attempts the actual blob delete; on success the id is dropped from the list; on
failure it stays, and the next write to that row (the next check, upload, or approval) retries
every pending id opportunistically. Consequences: the metadata switch (which artifact is
current) is always safe and immediate even when its predecessor's payload delete fails; no
artifact is ever deleted before its replacement's metadata has committed; repeated cleanup
attempts are idempotent (deleting an already-gone payload is a no-op, never an error); cleanup
for one Skill/account never touches another's blob, because obligations live on that Skill's
own row; and no unbounded orphan accumulation, because every row-write is also a retry point —
a payload can be stuck only until the next legitimate write to its own Skill.

**Review payload sufficiency (frozen):** for a changed **text** file, the artifact carries
both sides needed for human review — added: candidate content; removed: approved content;
modified: both. Unchanged files are never uploaded. For a changed **binary** file, the
artifact carries path, added/modified/removed, before/after size+hash, and `binary: true` —
never a raw binary preview, and never silently omitted from the review.

**Privacy boundary (frozen — a genuine, narrow exception to "Cloud never holds Skill
content"):** `stak skill check` is the explicit consent boundary for this upload. The
resulting artifact is account-private, owner-scoped, never published to any public STAK,
contains no Git credentials, no absolute/home-relative paths, no unrelated repository
content, and only the Skill-relative files a diff reports as changed — bounded in size, kept
latest-only, deleted when superseded or invalidated (§ above). Whole repositories and whole
approved Skill trees are never uploaded.

**Full approved-tree browsing is deferred (explicit intentional deviation from the
illustrative Final Contract design):** P5a does not upload every approved Skill file merely
to let the browser browse the complete approved tree outside an update review. Provenance,
history, and capabilities remain available normally; exact changed-file inspection is
available only when a review artifact exists. A full approved-tree file browser is a separate,
larger privacy decision, not resolved here.

**Approval-by-artifact (frozen — replaces a browser-supplied `candidateContentHash`):** the
web approves by immutable `reviewArtifactId`, never by submitting `candidateRevision`/
`candidateContentHash` itself. Cloud loads the authoritative stored artifact and verifies:
authenticated ownership, the artifact belongs to the named Skill, the artifact is the current
non-superseded artifact for that Skill, `artifact.approvedContentHash` matches the Skill's
current approved hash, and the artifact's status is update-available — only then approves the
candidate identity **stored in the artifact**. A no-longer-current artifact (superseded by a
newer check, or stale because the approved base already moved) returns an explicit
stale/superseded conflict, never a silent approval of something else.

**Approval is genuinely idempotent (frozen, final micro-gate — replaces delete-row-then-409):**
a successful approval does not delete its review-check row; it overwrites it with a
`'consumed'` tombstone — a repository-internal `sourceCheckState` never exposed through the
public Skills read model — recording exactly `skillId`, `reviewArtifactId`,
`candidateRevision`, `candidateContentHash`, and the row's prior (pre-approval)
`approvedContentHash`. The tombstone deliberately keeps that **old** base, so the existing
base-bound check (`stored.approvedContentHash === skill.contentHash`) naturally makes it
invisible as a live fact the moment approval advances the Skill — no change to that comparison
logic was needed. It retains no changed-file text; the payload is deleted via the same durable
cleanup obligation above. Replaying the identical `{skillId, reviewArtifactId}` after a lost
response — whether or not the payload delete has completed — re-detects the matching tombstone
and returns the **same successful result** again, without re-committing, re-deleting, or
resurrecting anything. If the Skill has since moved again (a later approval B landed), replaying
the earlier A's id against the now-stale tombstone is rejected with the same stale/superseded
conflict as any other no-longer-current artifact — a replay can never roll a Skill backward. A
superseded artifact that was never approved still returns the ordinary 409 conflict; only a
genuinely **consumed** (approved) artifact replays idempotently.

**`stak skill check [<skill>]` (frozen CLI command):** an explicit network operation using the
local machine's own Git/network credentials. With a Skill selector, checks one; without,
checks every desired Skill whose source semantics support checking. It never approves,
installs, pauses, or resumes anything. Per Skill it reports exactly one of: No update ·
Update available · Can't check for updates from this source · Check failed (with a safe
reason). It never exposes credentials or secret-bearing remote URLs.

**Local/pinned sources (unchanged P2 semantics):** Local never gets a remote check or a review
artifact. Dirty/ambiguous stays fail-closed. An exact-pinned commit with no tracked ref has no
moving upstream to check under existing P2 semantics — STAK never manufactures an "update
available" for it.

**Public-stack sources (audited, resolved — not a separate problem):** a Skill imported via
`stak use <stak>` carries forward the public stack requirement's own `restoration` field
**verbatim** (`packages/core/src/public-stack.ts`) — which is, in the real data model, always
either a plain Git `reference` (remote/ref/revision/path) or a `snapshot` (Local/dirty-origin).
There is no third, public-stack-native restoration strategy anywhere in the schema
(`referenceRestorationSchema`/`snapshotRestorationSchema` are the only two). A public stack
bundle is explicitly documented as **reference-only** (`packages/spec/src/public.ts`) — it
never carries Skill file content, only metadata plus a Git pointer. Consequence: `stak skill
check`'s existing Git-based materialization already resolves and reviews a public-stack-
originated Skill correctly and completely, with **zero special-casing** — because, structurally,
it already _is_ a Git-reference-backed Skill by the time it reaches this phase's code. The
separate `resolvePublicStackSourceLatest`/`PublicStackLocator`/`PublicStackVersionId` primitives
in `packages/core/src/skill-source.ts` remain defined but have no real caller today (no Skill's
restoration record uses the identity shape they resolve) — this is a pre-existing, orphaned
primitive from an earlier phase, not something this phase needs to wire up or remove.

## 6. Pause semantics

- A per-skill `paused: boolean` (default `false`; absent = active) is machine-local desired
  state carried in the lock. Retains version/provenance — **do not overload `remove`**.
- Resolver: a paused skill stays in STAK and the lock but is **excluded from agent
  projection**; `stak run` skips it. `stak skill resume` clears it.
- Desired `paused` may ride the pushed environment so the web can show it; per-machine effect
  is realised on next `run`. Migration: lock files from before this field still load.

## 7. Declared-capability field (optional)

- Capabilities (Read files / Write files / Run commands / Network) come from an **optional
  declared block in SKILL.md** only. Absent → UI shows "Capabilities not declared".
- V0 = source/trust info + declared capabilities when present. **No static analysis** of
  skill bodies (FUTURE). Never infer permissions from prose. "Asks for nothing new" means no
  declared-capability delta between approved and source versions.

## 8. Activity derivation (no events table)

Activity is **derived only** from existing records / deliberately-stored change timestamps —
**no general events table** (FUTURE):

- Memory backed up ← `memory_backups.created_at`
- Machine checked in ← `last_checkin`
- Update approved ← new imported version
- Project mapped / presence change ← check-in presence deltas
- STAK published ← `public_stack_versions`

**Truthfulness (Addendum §7):** never fabricate a historical event from a current-state
timestamp. If an activity type cannot be truthfully reconstructed from a real record or a
deliberately-stored change timestamp, **omit it** for 0.1.0.

## 9. Delete cloud Memory (**NEW**, destructive — narrow)

"Delete cloud Memory" deletes **STAK's server-held Memory backup data for the account** —
the Cloud backup payloads/metadata required to recover those Cloud copies. (Addendum §6.)

It **MUST NOT** delete: native agent Memory files, the local private STAK Memory store,
Skills, Projects, machine-local bindings, the STAK account; and it must **not** be confused
with project archive (archive never deletes).

**Recovery-method consequence (specify + test before building):** once Cloud backup payloads
are deleted, Protected recovery wrappers (`memory_recovery_methods`) that exist only to unlock
those Cloud copies become useless. Determine per-record whether they are invalidated or
removed as a consequence; document and test that behaviour in P3/P8 before implementation.
UI: typed-confirmation hard delete, worded that **local Memory is untouched but Cloud
recovery will no longer be available**.

## 10. Frozen language (customer-facing)

- **Skill:** Ready · Update available · Paused (+ note "Can't check for updates from this
  source"). A checkable source with no current CLI-reported result uses the plain, non-badge
  sentence "Updates haven't been checked yet." (§5a) — never collapsed into the cannot-check
  note, never a new primary badge.
- **Memory:** Backed up · Not backed up yet. Mode: Standard / Protected (account-wide).
- **Machine:** Up to date · Updates waiting · Last seen \<time\>.
- **Project:** Active · Archived · On this machine · Not on this machine.
- **General:** Needs attention.
- **Banned for normal states:** In sync, Online, Offline, Outdated, Lost, Broken, Unsafe.
  Each word appears only when its data condition holds; "Up to date" always with its
  check-in time.

**Needs attention** = union of: an update to review; a project not on the viewing machine; a
machine not seen in 30+ days; Protected Memory with no recovery method. Amber, never red
unless something actually failed.

## 11. Recovery naming

Recovery is a **recovery file** (`.stackkey`) or a **passkey** — not a typed "recovery key".
Design copy that says "recovery key" is renamed accordingly. The account-wide mode is
switched via `stak memory protect`.
